Counter Batch A: build plan 18 Oct 2026

Plan only: nothing is built, bumped or pushed. Source: the Batch A canvas (mockup) and his decisions of 18 Oct 2026. Planned from origin/master at bf00ee0c (v1163). Figures in the mockup are illustrative.

In one paragraph. Batch A ships as one salt-command version, one commit per part, after one salt-ds minor release that adds the missing recipes (rule 6: salt-ds first, then propagate to the Desk, the Counter and QR Command). The only part that changes data or routes is the per-order collection point (parts 2 and 3), so the version runs the full suite; every page part is display-only and is checked on its sections plus the gate as it goes. Nothing prices: no part reads or writes a price, floor, drift or row. Twelve Ask items wait on his answer, each with a recommendation.

2. The collection point, end to end

His decision: the point is set per order at Ready on Counter Admin, read by the Desk, and shown to the customer as a code ("Point A2") with a pin that opens the maps app. Ready today takes only status and mode, travels Counter Admin, then stmt/maker.js, then the Desk Worker, then the Counter's /desk/orders, then the order book. The point rides the same road.

2.1 The points list (part 2)

  • Store: Counter KV maker:points, {v:1, list:[{code, lat, lng}]}, at most 20. Modelled on Hours (maker:hours, stmt/hours.js): written by stmt/maker.js directly, no Desk hop. Never in git (the repo is public), never in the Desk build or the master.
  • Code: one capital letter and one or two digits, ^[A-Z][0-9]{1,2}$, so it can never match the roster-code pattern siteWords refuses and names no place. Shown as "Point A2" (pt.code).
  • Coordinates: typed as "lat, lng" or read from a pasted Maps link on the device (makerGeo.link, already in stmt/owner.js), rounded to 5 decimals, held within Malaysia's bounding box. No label, no address, no note field: nothing free-text that could carry a place name.
  • Routes: GET|POST /all/maker/points (verified owner, Access JWT plus the exact email), one shape per POST, validated by validatePoints. Removing a code an open order still sits at is allowed: the order holds its own copy (2.2).
  • Counter Admin: a Points card under Hours (loadMakerPoints, drawMakerPoints in stmt/owner.js): list, Add, Remove, Save.
  • Files: new stmt/points.js; stmt/maker.js; stmt/owner.js; stmt/words.js (Admin words); stmt/testfix.js (examplePoints, an invented list for the test accounts' Admin view, like exampleBulletin).

2.2 Ready carries the point (part 3)

  1. Counter Admin: "Ready to collect" opens a Sheet of the points (last used first, one 44px button each); a tap sends makerMove(order, {status:'ready', mode:'collect', point:'A2'}). "Ready to deliver" is unchanged and sends no point. makerMove keys its rid on order id plus body, so a different point is a different move with its own rid.
  2. stmt/maker.js: orderMoveFault admits point and counts a point-only body as a fourth kind of move (beside status, message and noReply); sameMove's key list gains point. The code's shape is checked up front; whether it is in maker:points is checked only after deskSeen says the move is new (refusal e.pointUnknown), so a retry of a landed Ready still answers {again:true} after A2 is removed (Fable 3).
  3. One resolver, both roads (Fable 4): resolvePoint(list, code) in stmt/points.js. Real orders: stmt/worker.js resolves from maker:points. Example orders never pass stmt/worker.js (stmt/maker.js goes to exampleAccount, then fixtureAccountMove): stmt/maker.js resolves from examplePoints. Either way pointAt travels as a sibling of body, merged into decideDesk's input after the seen check (the real desk op near orderbook.js 637-642; fixtureAccountMove near 402), and never into the stored request, which is built from body less rid (near 635) and compared whole (near 358).
  4. Desk Worker: src/worker.js rides Change point on the existing move action as {rid, point}, so its route regex and dispatch (near 1071, 1095-1107) need no new action (Fable 2). makerOrderFault (src/maker.js near 66, 114) widens its one-move count to the four kinds, checks the shape only, admits point only beside status:'ready' with mode:'collect' or alone (so never beside Decline, Cancel or a delivery), and refuses a mode:'collect' Ready without point; orderMoveFault applies the same rule; moveOrder (src/orders.js) relays the code. The Desk never sees coordinates (2.3).
  5. Order book (stmt/orders.js): decideDesk takes a point-only body in its own branch ahead of the status test (near 1043; today an empty status falls to "not a state the desk sets"), refuses a collect Ready with no resolved point (e.pointNeeded) and a point on a delivery; a Ready event is {kind:'status', status:'ready', mode:'collect', point, pointAt}, a Change point event {kind:'point', point, pointAt}; applyEvent sets order.point and order.pointAt, and its history line is {at, by:'desk', point} with no coordinates, since history travels whole (Fable 8). A part handover leaves both untouched (handover branch near 1273-1288; Fable 5). The point is a snapshot: editing or removing A2 later moves no order already at Ready.
  6. Change point: allowed while the order is Ready to collect with goods still to hand over (owedUnits, the same test as 2.3), its own rid, the same checks; wakes (near 1346, which keys on kind:'status' today) gains kind:'point' giving {k:'point-moved', o} (fixed words, no code in the banner); marksOf's default is right. It is undone by changing it back; it makes no ledger stage, so plan 4's Undo (undoOf, payments and handovers) is untouched. Nothing undoes a Ready today, and Batch A adds nothing that does.

2.3 Who reads what

  • Customer (customerView): point joins CUSTOMER_FIELDS. pointAt is not on the whitelist: customerView adds it only while status is ready, mode is collect and goods are still to be handed over. That third test matters: applyEvent sets status back to ready directly on a fix undo (near 1238) and on an amendment that leaves money owing (near 1269), and a customer who owes only money is not waiting at the point (Fable 6). After collection, cancellation or decline the code stays (Details reads "Collected at Point A2") and the coordinates leave every answer, the test fixture's included (tools/testfix.mjs passes orders through customerView).
  • Desk (Fable 1): the raw order doc leaves the Counter on five roads, and deskOrderView (drops pointAt) is applied on every one in stmt/worker.js: the /desk/orders GET (allOrders), both ?work=1 roads (ordersOwing), the replaceOrder answer and the deskMove answer, which src/worker.js hands straight to the Desk page. src/orders.js passes through what arrives, so the strip must be Counter-side. The deskseen op returns the raw doc to Counter Admin only, behind the owner's two locks: acceptable. The Desk reads point only, and its order line says "Point A2" (master, part 3b). Ready makes no ledger stage, so no note can carry it; an assertion holds that. The Desk's D1 holds no order doc.
  • Where coordinates do rest (Fable 9): his points in maker:points; each order's snapshot in the order book's event and order tables, its KV write-behind and the laptop's tools/orders-kv.mjs backups. All Counter-side or laptop, none in git; the backups stay gitignored.
  • Push: Ready keeps its words (news.ready-collect.*); the banner names no point. point-moved is added to stmt/sw.js kinds and news.*; sealedNews already lets only k, o, v, t, m through.
  • Maps link (page): pointHref(code, lat, lng): https://maps.apple.com/?ll=LAT,LNG&q=Point%20A2 on iPhone, iPad and Mac; geo:LAT,LNG?q=LAT,LNG(Point%20A2) on Android; https://www.google.com/maps/search/?api=1&query=LAT,LNG elsewhere. The label is the code only. The mockup's ?q=Point%20A2 searches the words and finds nothing; the build uses the coordinates. A plain navigation: CSP unaffected, no third-party load (rule 4).
  • Leak checks: the public desk scan (verify 654) and tools/ledger.mjs already pass a code like "A2" (too short, no roster shape). New assertions: no lat/lng of pointAt in public/desk.html, any ledger note or any Desk answer.
